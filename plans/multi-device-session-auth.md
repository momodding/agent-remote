## Context

Web client pairs, opens a terminal, but it is unusable; Android then fails with 401. Two independent root causes, both confirmed by reading the code (not inferred):

1. **No real PTY execution exists anywhere in the backend.** `backend/internal/session/manager.go`'s `Input()` never runs `Command`/`Args` — there is no `os/exec`, no pty library in `backend/go.mod`, anywhere in `backend/`. It only appends the typed bytes to scrollback and re-broadcasts the *same bytes* back as `pty.output` (manager.go:150-173, specifically the `m.enqueue(... Data: base64.StdEncoding.EncodeToString(chunk) ...)` at line 172). This is a loopback stub, not a shell — the terminal is unusable for every device, not just the second one.
2. **Bearer-token auth already supports unlimited concurrent devices** (`SessionStore.Verify` in `auth.go:177-187` scans an array and never revokes), but the QR **pairing** token is deliberately single-use and rotates every 45s / expires after 2 minutes (`docs/protocol.md`, `pairing.go:112-126` `Consume` deletes the record on success). A second device has no way to get its own pairing without racing the same rotating QR the first device may have already consumed, or without being physically present when a fresh QR prints. Failing that handshake leaves the client with no bearer token, so any subsequent REST/session call is sent unauthenticated and hits `withAuth` → 401 (`server.go:401-417`).

End state: (a) sessions run a real shell process end-to-end (input reaches the process, output comes from the process, resize/close act on the real process), and (b) an already-authenticated device can mint a fresh, independent pairing on demand so a second device gets its own bearer token without touching or racing the first device's session or the terminal-displayed QR.

## Approach

Two independent workstreams — different files, no shared edits, safe to do in either order or in parallel.

### 1. Real PTY execution (`backend/internal/session/manager.go`, `backend/go.mod`)

1. Add the dependency: from `backend/`, run `go get github.com/creack/pty@v1.1.24`. This updates `go.mod`/`go.sum`; do not hand-edit either. `pty.StartWithSize`/`pty.Setsize`/`pty.Winsize` compile on every existing Makefile `DAEMON_TARGETS` (linux/darwin/windows) since creack/pty ships Windows-build-tagged stubs — on Windows they return `pty.ErrUnsupported` at *runtime*, not a compile failure. This is a pre-existing gap (Windows daemon has never run real shells either, since nothing ran at all before this fix) — not a regression, out of scope to close now.
2. Add `cmd *exec.Cmd` and `ptmx *os.File` fields to `sessionRuntime` (manager.go:50-58), plus `exitOnce sync.Once` for idempotent exit handling.
3. Rewrite `Manager.Create` (manager.go:87-127): after resolving `command`/`cwd` as today, default `cols, rows := req.Cols, req.Rows` to `80, 24` when `<= 0`. Build `cmd := exec.Command(command, req.Args...)` with `cmd.Dir = cwd` (leave `cmd.Env` nil — inherits the daemon's environment, matches Go's default). Call `ptmx, err := pty.StartWithSize(cmd, &pty.Winsize{Rows: uint16(rows), Cols: uint16(cols)})`; on error return `nil, err` exactly like the existing `appendScrollback` error path (so `handleSessions` still turns it into `400 create_failed` and calls `s.limits.EndSession()` — no server.go change needed). Store `cmd` and `ptmx` on the runtime. Set `meta.State: StateRunning` (a process is now actually running; there is no test asserting `StateIdle` at creation — confirmed via repo-wide grep). After registering the runtime and its `go m.forward(runtime)` line, add `go m.readOutput(runtime)`.
4. Add `func (m *Manager) readOutput(runtime *sessionRuntime)`: loop `runtime.ptmx.Read(buf)` (32KB buffer), call `m.recordOutput(runtime, chunk)` for `n > 0`, and on any read error call `m.markExited(runtime)` and return. This is the ONLY place PTY output enters the pipeline now.
5. Extract the existing scrollback/detector/preview/broadcast body of `Input` (manager.go:159-172) into `func (m *Manager) recordOutput(runtime *sessionRuntime, chunk []byte)`, unchanged except: after the `detector.Push` branch, add an `else if runtime.meta.State == StateWaiting { runtime.meta.State = StateRunning }` so state recovers once new output arrives after a wait. Keep ignoring `appendScrollback`'s error the same way the rest of this file ignores best-effort I/O errors (e.g. `_ = os.Remove(...)` in `Close`) — do not add a logger.
6. Rewrite `Manager.Input` (manager.go:150-174) to: look up the runtime, return `errors.New("session not found")` if missing, return `errors.New("session not running")` if `runtime.ptmx == nil` (restored/dead sessions from `restore()`), else `_, err := runtime.ptmx.Write(b); return err`. It no longer touches scrollback, detector, or the outbound queue directly — `readOutput`/`recordOutput` owns all of that now, which also removes the prior data race where `Input` mutated `runtime.meta`/`runtime.plain` without holding `m.mu`.
7. Rewrite `Manager.Resize` (manager.go:176-186): keep the existing `cols <= 0 || rows <= 0` validation, then if `runtime.ptmx != nil` call `return pty.Setsize(runtime.ptmx, &pty.Winsize{Rows: uint16(rows), Cols: uint16(cols)})`, else `return nil` (no-op for dead/restored sessions, matching today's permissive behavior).
8. Add `func (m *Manager) markExited(runtime *sessionRuntime)` guarded by `runtime.exitOnce.Do(...)`, containing exactly the state-transition body currently inline in `Close` (manager.go:198-203: set `StateExited`, `detector.Exited()`, `WaitState`, `UpdatedAt`, `m.notify`, `m.emitState`) plus `_ = m.saveMetadata()` at the end. This makes exit-handling idempotent whether triggered by `Close()` or by the child process dying on its own (e.g. the user types `exit`).
9. Rewrite `Manager.Close` (manager.go:188-209): after removing the runtime from the map, add `if runtime.cmd != nil && runtime.cmd.Process != nil { _ = runtime.cmd.Process.Kill() }` then `if runtime.ptmx != nil { _ = runtime.ptmx.Close() }`, then call `m.markExited(runtime)`, then `_ = os.Remove(runtime.scrollback)`, then `return nil`. // ponytail: `Process.Kill()` only signals the direct pty child, not its whole process group — a backgrounded grandchild (`sleep 300 &`) can be orphaned. Upgrade path: a unix-only `syscall.Kill(-pid, SIGKILL)` build-tagged file if orphaned children become a real problem; skipped now because it needs a second Windows-safe file for zero observed benefit today. This intentionally changes `Close`'s return value from propagating `saveMetadata`'s error to always returning `nil` on success (the only contract any test exercises is "session not found" → non-nil; treat metadata persistence the same best-effort way `os.Remove` already is on the very next line).
10. Rewrite `Manager.Subscribe` (manager.go:139-148): before `runtime.subs = append(...)`, add `if data, err := os.ReadFile(runtime.scrollback); err == nil && len(data) > 0 { fn(protocol.PTYOutputEnvelope{Type: "pty.output", SessionID: id, Data: base64.StdEncoding.EncodeToString(data), Seq: runtime.seq}, protocol.SessionStateEnvelope{}) }`. This calls `fn` synchronously and directly, the same calling convention `forward` already uses (`sub(output, state)`) — it is what makes a second device's terminal show the existing screen content immediately instead of staying blank until the next new byte arrives, which is the concrete "connect from multiple devices" fix for the terminal view itself.
11. Fix the test-leak this introduces: `newBootstrapServer` in `backend/internal/server/server_test.go` (219-247) now spawns a real `/bin/sh` per `srv.sessions.Create(...)` call made in any test using it. Add, inside `newBootstrapServer` right after constructing `srv`, `t.Cleanup(func() { for _, sess := range srv.sessions.List(context.Background()) { _ = srv.sessions.Close(sess.ID) } })`. This is the single choke point every test routes through (`TestSessionWSRejectsPTYBeforeToken` and `TestSessionWSAcceptsPTYAfterToken` currently create a session and never close it), so fixing it there reaps every leaked shell process regardless of which test forgot to close.
12. Add `TestPTYExecutesRealCommandAndSeedsNewSubscriber` to `backend/internal/server/server_test.go`: create a session with `protocol.CreateSessionRequest{Name: "test", Command: "sh", Args: []string{"-c", "echo agentic-remote-marker-123"}}` (send no `pty.input` at all — the old stub had nothing to echo without input, so this test is impossible to pass against the pre-fix code, which is exactly the point). Poll `srv.sessions.List(context.Background())[0].Preview` for up to the test's existing timeout pattern until it contains `"agentic-remote-marker-123"`. Then call `srv.sessions.Subscribe(summary.ID, fn)` with a second callback and assert that callback is invoked synchronously with an envelope whose decoded `Data` also contains the marker, proving the scrollback-seed-on-subscribe behavior from step 10.

### 2. On-demand additional pairing (`backend/internal/security/auth.go`, `backend/internal/server/server.go`, `client/lib/src/services/agentic_remote_api.dart`, `client/lib/src/features/dashboard/session_dashboard.dart`)

1. Add `func (a *AuthService) NewPairing(endpoint, fingerprint string, skipFingerprintVerification bool, now time.Time) (*PairingPayload, error) { return a.pairings.Create(endpoint, fingerprint, skipFingerprintVerification, now) }` to `auth.go`, right after `SetPairedHook` (auth.go:84-88). This reuses `AuthService`'s existing private `pairings *PairingStore` field — no new `Server` field, no `server.New(...)` signature change, no call-site churn in `main.go` or `server_test.go`. Because `PairingStore.Pairings` is an array keyed by ID (not a single overwritten slot — confirmed via `pairing.go:93-126`), this mints an independent, additional, single-use pairing record that coexists with whatever the CLI's `rotatePairing` loop is currently displaying; it does not touch, replace, or invalidate that QR or any existing bearer token.
2. Add `func (s *Server) handlePairingCreate(w http.ResponseWriter, r *http.Request)` to `server.go`, next to `handleNotifyRegister` (server.go:285-296): reject non-POST with `w.WriteHeader(http.StatusMethodNotAllowed); return` (matching the `default:` case style already used in `handleSessions`, server.go:164-166), else call `s.auth.NewPairing(s.cfg.PublicEndpoint, s.tls.Fingerprint, s.cfg.SkipFingerprintVerification, time.Now().UTC())`, write `500 pairing_failed` on error (`protocol.ErrorEnvelope{Type:"error", Code:"pairing_failed", Message: err.Error()}`) else `writeJSON(w, http.StatusCreated, payload)`. Register the route in `Handler()` (server.go:56-73): `mux.HandleFunc("/v1/pairing", s.withAuth(s.handlePairingCreate))`. `security.PairingPayload`'s existing JSON tags (`v`, `endpoint`, `fingerprint`, `pairingId`, `token`, `expiresAt`, `skipFingerprintVerification`) already match the Dart `PairingPayload.fromJson` exactly (`client/lib/src/protocol/messages.dart`), same as the CLI-printed QR JSON — zero new serialization to design.
3. Add `Future<String> createPairing() async { final response = await client.post(agenticEndpointUri(pairing!.endpoint, '/v1/pairing'), headers: _headers()); if (response.statusCode != 201) { throw StateError('create pairing failed: ${response.statusCode}'); } return response.body; }` to `AgenticRemoteApi` in `agentic_remote_api.dart`, next to `closeSession` (near line 300). Returns the raw JSON body text directly — no `PairingPayload.toJson()` needed since the caller only displays it verbatim for the user to relay to a second device, exactly like the CLI's own raw-JSON-alongside-QR output (`printPairing` in `main.go:267-275`).
4. In `session_dashboard.dart`'s `_SessionDashboardState` (session_dashboard.dart:20-29), add `String invitePayload = '';` alongside the existing `connectionError` field. Add a `ShadButton.outline` labeled `'Invite device'` next to the existing `'New session'` button (around line 70-86), `onPressed` calling `widget.state.api.createPairing()`, on success `setState(() => invitePayload = result)`, on error reuse the existing `catch (error) { setState(() => connectionError = error.toString()); }` pattern already used by the two adjacent buttons. Below it, `if (invitePayload.isNotEmpty) ...[const SizedBox(height: 8), ShadInput(controller: TextEditingController(text: invitePayload), readOnly: true, maxLines: 6)]` — reuses the already-imported `ShadInput` widget, no new package.
5. Add `TestPairingCreateMintsIndependentDevice` to `backend/internal/server/server_test.go`: use `newBootstrapServer(t)` to get `srv, pairings`; obtain device-A's token via the existing `testBearerToken(t, srv, pairings)` helper; `POST /v1/pairing` with `Authorization: Bearer <deviceA token>` through `srv.Handler()` via `httptest`, expect `201`; `json.Unmarshal` the body into a `security.PairingPayload`; complete a second Auth-v2 handshake against `/v1/ws/sessions/bootstrap` using that payload's `PairingID`/`Token` (same steps `testBearerToken` already performs — extract that handshake body into a small helper parameterized by a `*security.PairingPayload` if easiest, or inline it) to obtain device-B's `sessionToken`; assert `deviceBToken != deviceAToken` and both `srv.auth.Verify(deviceAToken)` and `srv.auth.Verify(deviceBToken)` are `true` — proving both devices hold independent, simultaneously-valid credentials.

## Assumptions & contingencies

- Windows daemon builds (`make daemon-build DAEMON_TARGETS=windows`) will still compile after adding `creack/pty`, but `Manager.Create` will return `pty.ErrUnsupported` at runtime on Windows — real shell sessions have never worked on Windows before this change either (nothing executed at all), so this is a pre-existing gap surfaced honestly instead of a new regression; closing it (ConPTY support) is out of scope for this fix.
- `Close()`'s process termination only kills the direct pty child (`cmd.Process.Kill()`), not its full process group/tree, even though `docs/protocol.md` describes close as terminating "the PTY process tree." A cross-platform-safe process-group kill needs a unix-only build-tagged file (since `syscall.Kill` doesn't exist for `GOOS=windows`, and this repo's Makefile cross-compiles a windows daemon target) — skipped as speculative until an orphaned-grandchild-process problem is actually observed, per the ponytail comment left in the code at that exact spot.
- The "Invite device" flow displays raw pairing JSON text for the user to manually relay (copy/paste, screenshot, etc.) rather than rendering a second on-device QR image, since the client has no QR-generation package today (only `mobile_scanner` for scanning) and adding one is unwarranted for a few lines of copyable text — matches the CLI's own existing "or paste the raw JSON payload" fallback path already documented in `docs/protocol.md` and `docs/android-daemon-connect.md`.
